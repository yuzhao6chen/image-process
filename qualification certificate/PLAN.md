# 企业资质材料自动入库方案

> 状态：待评审，尚未实现。
> 更新日期：2026-09-03。
> 本文替换原图片抽取方案。本次只编写方案，不修改解析代码、不执行迁移、不启动任务、不调用模型或写入数据库。

## 1. 目标与推荐方案

目标：图片解析完成后，系统自动确定所属企业，判断新增、补充、归档或待确认，并将可用信息显示在对应企业画像中。

采用“自动归档 + 规则控制发布 + 异常人工确认”：

- 企业归属明确、内容无冲突：自动关联已有资质、补充证据；符合发布策略的新条目自动进入画像。
- 已过期材料：保存历史版本，不当作当前有效资格。
- 企业归属、日期、等级等存在冲突：保存候选及差异，不覆盖当前值，交由人工确认。
- 自动发布只代表资料可以展示和使用，不代表证书真实性已通过官方核验。

首期处理企业资质、行政许可证、体系认证及相关审核报告。施工许可先归档为项目材料，后续正式投影；员工证书、财务报告不在本轮实现范围内。

## 2. 当前基础与本批材料的增量

### 2.1 当前链路

现有 extract_company_images.py 已支持逐图识别、JSON/Markdown 输出、错误记录和断点，但尚无向后端提交结果并发布的入口。

数据库已有 company_qualification、company_profile_field_value 及来源、附件、投影运行等模型，存在以下接入障碍：

1. company_qualification 缺少范围、认证标准、证据关联和可靠的业务唯一键，status 默认值仍是 VALID。
2. company_profile_evidence_attachment 要求已确定 companyId，且主要关联旧的补录/纠错记录，不适合承载企业尚未匹配的任务。
3. 现有企业画像投影仅在服务启动时扫描一次，不是持续监听图片结果的队列。
4. 统一画像的 qualification.items 从多个来源选择一个候选数组，而非逐项合并。只写数据库不保证页面和推荐能读到全部资质。
5. 当前类型不符合英文枚举时会归为 unknown，随后清空资质数组；原始模型返回也没有完整保留。

## 3. 自动化流程与职责

    图片解析
       ↓
    原始返回 + 归一化结果 + 文件内容哈希
       ↓
    提交后端，取得持久化任务编号
       ↓
    存原图和候选 → 企业匹配 → 类型与字段校验
       ↓
    逐条比较已有数据：新增 / 补充 / 重复 / 历史 / 冲突
       ↓
    规则允许的条目自动发布，其余待确认
       ↓
    画像、资质列表、推荐和语义索引使用统一结果

职责划分：

- Python：解析、保存结果、提交任务、查询回执，不直接写业务数据库。
- 后端：授权、独立校验、企业匹配、合并、事务、发布与撤回。
- 后台 worker：领取持久化任务、执行有限重试和发布。首期使用现有技术栈，不引入 Redis/Kafka。
- 页面：查看处理结果、来源证据和差异，只对异常条目进行确认。

先保留本地命令行使用方式，再增加网页上传；两种入口必须调用同一套入库规则。

## 4. 提取契约 V2：入库前的必要改造

下列类型和字段均为拟新增，不是当前已经实现的接口。

| 文档类型 | 主要内容 | 目标 |
|---|---|---|
| COMPANY_QUALIFICATION | 行业资质、具体专业、等级、承包范围 | 企业资质条目 |
| COMPANY_LICENSE | 安全生产等行政许可、许可范围 | 企业许可条目 |
| COMPANY_CERTIFICATION | 体系名称、标准、认证范围 | 企业认证条目 |
| CERTIFICATION_REPORT | 审核类型、日期、决定、对应认证线索 | 已有认证的附件与审核事件 |
| CONSTRUCTION_PERMIT | 项目、许可编号、单位及人员角色、金额 | 项目材料候选 |
| UNKNOWN | 不明确的文档 | 仅归档和待确认 |

资质、许可、认证继续使用 company_qualification，不必首期重建全部画像表，但必须显式区分类别，并与项目 requirementSubtype 建立映射。

每份结果至少保存：

- 文件信息：内容 SHA-256、文件名、类型、大小、原图引用。
- 处理版本：模型、提示词版本、提取器版本、归一化版本、schemaVersion、时间、请求编号。
- 企业信息：材料中实际出现的持有人名称、信用代码、角色；与“用户指定的目标企业”分开保存。
- 条目信息：原始/标准名称、证件类别、专业、等级、证书号、发证日、有效起止日、发证机构、范围、标准编号。
- 字段证据：原文、图片/页码、字段路径；坐标只有可靠获取时才保存，不编造。
- 质量信息：缺失、冲突、规则错误码、置信度、原始模型输出。
- 状态信息：材料载明的状态、日期推导的时间状态、核验状态分开记录。

解析端必须调整：

1. 明确的中文同义类型做白名单转换；宽泛的“资质证书”不能无条件解释为施工资质，有歧义就待确认。
2. 先保存原始模型返回，再归一化。类型错误不能清空已抽取字段，只记录错误并阻止发布。
3. 提示词分别描述枚举并给出合法 JSON 示例，不把多个选项用“|”拼成一个示例值。
4. 文件身份改为内容哈希，不再依赖路径、大小和修改时间；新版本结果不能覆盖旧版本。
5. 不混淆发证日与有效起始日。非法日期和单位不明确的金额保留原文，不强行转换。
6. confidence 或 review_required=false 不能绕过后端校验。

V1 结果只进入候选层。原图可访问、字段完整的记录经显式适配后使用；已丢失字段的记录重新抽取或人工补正，不能用零散 evidence 冒充完整结果。重新调用模型需要另行授权。

## 5. 企业归属：如何进入“对应公司”

后端先检查提交者有权处理哪些企业，再进行匹配。模型返回的 companyId、文件夹名称和请求参数都不是授权依据。

1. 信用代码格式及校验位正确、精确命中已授权企业，并且持有人名称一致或属于已确认别名：自动绑定。
2. 信用代码缺失，但上传会话已绑定企业，持有人名称精确匹配该企业或已确认别名：可绑定为补充材料；存在同名歧义则停止。
3. 管理员批量导入可以指定目标企业，但不能绕过持有人冲突校验。
4. 只有模糊名称、多个匹配结果、信用代码与名称矛盾：进入 NEEDS_REVIEW。
5. 属于另一家企业：不得发布到当前企业，也不得为普通用户自动写入另一家公司。
6. 库内找不到企业：不自动创建或合并企业，由有权限的人员确认后处理。

一张材料中的施工单位、监理单位、审计机构要分别识别。不能把所有姓名和证书都归属于上传企业。信用代码校验通过也只证明格式正确，不证明材料真实。

## 6. 发布规则：哪些自动、哪些确认

### 6.1 候选入库与业务发布分开

- 候选入库：保存原图、提取结果和异常，可以追溯，不改变当前有效资质。
- 业务发布：经过规则或人工确认，关联或新增正式条目，进入画像。

首期启用自动归档及已有证书的无冲突证据关联；小样本核对后，由管理员显式开启“自动新增、补充空字段”。仅治理这条机器导入通道，不恢复所有画像字段的旧审核流程。

### 6.2 逐项动作

| 情况 | 处理 |
|---|---|
| 企业、证书号和具体条目身份相同，内容一致 | 关联新证据或返回重复，不新增资质 |
| 已有范围、标准等为空，新材料有明确证据且无冲突 | 发布策略允许时补空字段，记录每个字段的来源 |
| 新条目归属明确、核心字段完整、规则通过 | 策略允许时新增“材料提取、未核验”条目 |
| 非空日期、等级、持有人、范围存在差异 | 保存差异等待确认；可先归档原图，不覆盖旧值 |
| 证书已过期 | 保存历史版本，不参与当前有效资格判断 |
| 监督审核报告能唯一匹配已有认证 | 保存报告日期、结论和附件，不新增资质、不自动续期 |
| 未知类型、缺编号、原图缺失或核心字段无法确认 | 仅候选归档，明确补充要求 |

自动新增至少要求：原图可追溯、身份匹配通过、类型与条目名称/编号明确、核心字段有证据、日期关系合理、关键警告已解决、结构校验通过。置信度阈值以后根据样本评估配置，不能把一个固定阈值当作准确率保证。

有效期未载明、长期有效等特殊情况首期待确认；不自动补到期日。不能按“有效期更长、等级更高、上传更晚”直接选择冲突值。

### 6.3 去重与变更

区分三种身份：

- 文件身份：授权范围内的内容 SHA-256，相同图片改名不重复处理。
- 提取版本：文件身份 + 模型/提示词/提取器/归一化版本。重新抽取不等于新增业务资质。
- 条目身份：企业 + 证件类别 + 规范化证书号 + 具体资质或认证名称；等级、有效期变化进入版本比较。

同一证书号包含总承包和钢结构两项资质时分别保留。中文数字、括号、空格等归一化可回溯；没有依据的名称别名不强行合并。

换证号、升级、续期需要明确关联依据，不能只凭相同名称认定旧证失效。保留历史版本和变更前后值。一张材料可以关联多条资质，多张材料也可以共同支持一条资质。

## 7. 存储和模型调整

延续现有 MinIO、MongoDB、MySQL 分工。以下新增模型和字段均为设计建议。

| 存储 | 保存内容 |
|---|---|
| MinIO | 原始图片，独立私有企业材料 bucket；对象键由后端按授权范围及哈希生成 |
| MongoDB | 新集合 company_document_extractions，保存不可变的原始返回、归一化候选、字段证据和提取版本 |
| MySQL | 文件/任务索引、企业绑定、正式资质、证据关联、发布审计 |
| 画像读取层 | 规范化的合并结果，不为每张图片建立一套互相竞争的生效数组 |

### 7.1 新增 CompanyDocumentImport

兼作文件索引、持久化任务和回执，包含：

- UID、批次、提交人、授权归档范围、指定企业与最终匹配企业。
- 文件哈希、元信息、MinIO 引用、MongoDB 提取版本引用。
- 状态、重试次数、下次重试时间、worker 租约、错误码、逐项结果摘要。
- 唯一幂等键：授权范围 + 文件哈希 + 提取版本，使用固定长度摘要。

尚未匹配时允许最终 companyId 为空，但访问权限仍由提交者和授权范围控制。不能仅因未匹配企业就公开文件。

### 7.2 扩展 CompanyQualification

保留现有表和核心字段，补充：

- 明确证件类别、专业、范围、认证标准、有效起始日、核验状态。
- 可空唯一 identityKey，由服务端根据条目身份生成，不依赖包含 NULL 的组合唯一键去重。
- 新记录 status 默认改为 UNKNOWN，不在迁移中批量修改历史 VALID 或替其补造核验结论。

来源证据通过单独绑定保存，不能用一个 sourceRef 覆盖全部来源。旧记录的 identityKey 可以暂为空；多个已有记录同时命中时待确认，不自动删除。存量去重单独评审。

### 7.3 新增 CompanyQualificationEvidence

支持文件与资质的多对多关系，保存资质 ID、导入任务、提取版本、稳定条目标识、证据角色、字段来源、报告日期及时间范围。

增加绑定唯一键，保证重试不重复追加证据。模型数组下标不作为跨版本稳定 ID。

### 7.4 新增 CompanyDocumentPublishEvent

保存操作人或自动策略版本、动作、目标记录、变更前后的小范围字段值及证据绑定。动作键唯一，与业务写入处于同一 MySQL 事务，用于重试和撤回。不存完整模型 JSON 或图片 Base64。

原投影运行/错误/引用表依赖 snapshotUid、apiCode 等 API 快照语义。复用其设计思路，但首期不伪造 API 编号来塞入图片任务，原投影链保持不变。

### 7.5 来源与核验状态

- 增加 DOCUMENT_OCR 材料来源，不伪装为 USER_INPUT 或 MONGODB_API；若加入 ProfileSourceType，同步数据库枚举、DTO、来源标签和事实解析器。
- 自动提取/发布仍为 UNVERIFIED；人工确认可用 USER_CONFIRMED。SYSTEM_VERIFIED 只用于有可追溯外部核验依据的结果。
- “按日期尚未到期”不等于真实有效。材料状态、时间状态和核验状态分开；不能仅凭到期日写 VALID。
- 已发布未核验材料可以展示，但不能独自支撑资格判断 PASS。
- 读取或资格判断时按指定业务日期重算是否过期，不永久使用解析当天的缓存状态。

api/prisma/schema.prisma 与 crawler_prisma/prisma/schema.prisma 按仓库约定对齐，迁移实际执行一次。添加约束前先只读查看存量冲突，不用清库或 seed 解决。

## 8. 保证入库后真正被系统使用

入库与读取改造必须一起实施：

1. 基于现有 companyQualificationFacts.ts，增加类别、范围、标准、证据和发布/核验信息，复用统一合并规则。
2. qualification.items 合并 API 来源、业务表和已发布材料的条目，不能只按数组完整度挑一个来源；未发布候选不能混入。
3. 保留用户覆盖和主动清空语义。机器导入不能覆盖 USER_INPUT；被用户值覆盖时提示“资料已入库，但未作为当前生效值”。
4. 统一画像、独立资质列表、推荐/投标分析及语义索引读取相同规范化结果；DTO 不丢失范围、日期和来源。
5. 页面分别展示当前资料、历史、冲突和待核验状态；证书详情可查看原图及审核报告。
6. 发布提交后，通过可重试任务触发现有语义同步机制刷新该企业。索引失败不撤销成功归档，但不能报告“索引已刷新”。

完整的等级/许可范围硬规则匹配另行推进；本轮至少避免未核验图片资料因字符串命中而被直接判定合格。

## 9. 解析完成后如何触发

### 9.1 本地入口

保留纯本地解析作为默认方式。拟新增参数，当前不能直接运行：

- --submit：逐图解析后提交，不绕过后端发布策略。
- --company-id：可选目标企业提示，仍需服务端核对权限和持有人。
- --batch-id：批次追踪标识，不作为归属依据。

新增提交适配器上传原图、发送结果、保存任务 UID、查询回执。地址和最小权限凭据独立配置，解析脚本不接收数据库密码。

提交失败保留待提交清单，再次提交不重复调用模型。请求超时先按幂等键查询服务端，不能直接创建新的业务记录。

### 9.2 后端与 worker

拟新增提交、查询、差异预览、确认/拒绝、重试和撤回能力。具体路由及上传协议实施时确定，不复用“用户编辑画像字段”接口冒充机器导入。

后台 worker 周期领取 MySQL 持久化任务：

- 用条件更新或事务抢占任务，设置租约及恢复条件，避免多进程重复执行。
- 发布前再次检查企业授权、现有条目和审核版本，防止使用过时结论覆盖新数据。
- 同一企业的资质合并进行数据库级串行控制，并辅以唯一约束；“先查后插”不足以防并发重复。
- 服务重启恢复未完成任务；网络和外部存储故障有限重试，超限进入失败列表。
- 企业归属不明和字段冲突不属于网络异常，不靠反复重试解决。

网页上传和目录监听放在这条通道稳定之后。目录监听需确认文件写入完成并结合哈希去重，不能只靠一次文件事件判断导入成功。

### 9.3 状态和用户回执

任务阶段拟定：

    RECEIVED → STORED → VALIDATING → PROCESSING
                                      ↓
              COMPLETED / PARTIAL_REVIEW / NEEDS_REVIEW / FAILED

逐条结果分别记录 CREATED、ENRICHED、EVIDENCE_LINKED、DUPLICATE、HISTORICAL、NEEDS_REVIEW、REJECTED。一张图有多条资质时允许部分成功，不能用一个成功标志掩盖剩余问题。

回执示例：

- 已关联北京城建六建设集团有限公司，补充两项资质证据，未重复新增。
- 安全生产许可证已保存为历史版本，仍需当前有效材料。
- 到期日期存在差异，等待确认，原值未更改。
- 材料属于其他企业，本批未发布。

## 10. 一致性、安全与撤回

- 三种存储没有共同事务：先保存不可变原图和提取文档，确认可读取，再以 MySQL 事务提交业务条目、证据绑定、发布审计和逐项完成状态。
- 使用稳定引用和动作幂等键重试。业务已提交但回执丢失时返回原完成结果，不再次写入。
- 正式条目不得指向保存失败的证据。孤立对象标记待处理，按另行批准的保留策略清理，不在失败重试时递归删除。
- 上传校验实际内容类型、大小和哈希；禁止把任意本地路径或 URL 当作后端读取指令，避免越界读取和 SSRF。
- 原图私有，下载按企业授权，链接短时有效。普通日志不记录凭据、身份证号、Base64 或完整敏感资料。
- 调用模型前明确第三方处理范围；导入已有结果默认不再次上传到模型服务。
- 撤回仅撤销该来源绑定及其贡献；存在其他来源或后续人工变更时不盲目恢复旧值，应重新计算或转人工确认。
- 暂停自动发布不影响已有资料查看。回退保留新增表、附件和审计，不破坏历史记录。

## 11. 实施阶段

| 阶段 | 内容 | 完成标准 |
|---|---|---|
| A：稳定提取 | 修复类型归一化、字段丢失，增加 V2、原始返回及内容哈希 | 本批材料可正确分类和追溯，旧结果有明确兼容或待确认路径 |
| B：归档与预览 | 接收原图和结果、持久化任务、企业匹配、差异比较 | 每份材料有任务编号；不误归属；先不开启自动新增 |
| C：发布与读取 | 必要迁移、合并、证据绑定、审计、确认、统一读取 | 补充内容在页面及消费端可见；用户覆盖不丢失；未核验不自动 PASS |
| D：持续自动化 | 解析后提交、常驻 worker、有限重试、回执和索引刷新 | 正常材料自动完成，异常可恢复、可确认、可撤回 |

在 C 阶段先人工确认少量样本，再显式开启验证过的自动动作。

施工许可后续拟新增独立事实模型，允许 projectId 暂为空，保留许可编号、企业角色、人员角色和证据。项目未匹配时不制造虚假项目；金额须确认单位后转为“元”，不凭许可证创建缺少合同证据的 Contract，也不标记已竣工。

## 12. 建议验证场景与边界

| 场景 | 预期 |
|---|---|
| 同图改名、重复提交、超时后重试 | 不重复新增条目和证据 |
| 同号包含多项资质、多图支持同一证书 | 各项分别保留，来源可合并 |
| 多张材料分别导入同一企业 | 画像读取完整合并结果，不只展示一个数组 |
| 会计师事务所材料指定为北京城建六 | 归属冲突，不发布 |
| 过期、尚未生效、有效期不明 | 分别保留时间状态，不一律标 VALID |
| 日期相差一天、认证范围条款不同 | 展示冲突，确认前不改旧值 |
| 体系覆盖人数 402、旧证书法人不同 | 不改当前员工数、法人 |
| 提交中断、存储不可用、worker 重启 | 已成功部分可恢复，失败不污染正式数据 |
| 并发导入、后续人工修改、撤回旧批次 | 无重复和丢失更新，不覆盖后续变更 |
| 用户覆盖/清空 qualification.items | 保留用户意图，明确资料是否生效 |
| 仅有未核验材料与项目要求关键词匹配 | 资格结论待核验，不直接 PASS |

本次未执行上述验证。后续只有用户明确授权才运行测试、迁移或服务。新增接口、参数及定向测试命令实施后再提供；不用 db:seed、db:rebuild 或迁移重置验证入库。

## 13. 本轮建议先做的闭环

先实现：

**解析结果自动提交 → 正确关联公司 → 自动补已有资质证据 → 新增/冲突可预览确认 → 画像统一可见。**
